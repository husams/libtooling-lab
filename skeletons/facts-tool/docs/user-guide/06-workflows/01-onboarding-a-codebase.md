# Workflow: Onboarding a Codebase

## Goal

Bring a real C++ codebase under `facts-tool` analysis end to end: register
it, import its compile database, extract full symbol facts, confirm what
actually got extracted, and understand what "incremental" does and does not
mean before you rely on it.

This walkthrough uses `facts-tool` analysing its **own** C++ source tree as
the target: 212 `.cpp` files under `src/`, with real inheritance from Clang
base classes, virtual dispatch, templates, and lambdas. All generated
databases go to a scratch directory, never inside the checkout being
analysed.

## Prerequisites

- A built `facts-tool` binary (see
  [Installation](../01-introduction/03-installation.md)).
- A target codebase with a `compile_commands.json` already generated by its
  build system. Here that is the `facts-tool` checkout's own
  `build/compile_commands.json`.
- A scratch working directory for the generated project and facts
  databases.

## Steps

### 1. Register the repository

```console
$ facts-tool repo add facts-tool /path/to/facts-tool --conf project.sqlite
Repository registered
$ facts-tool repo show facts-tool --conf project.sqlite
ID	NAME	KIND	COMPONENTS	CLONES	ACTIVE CLONE
1	facts-tool	repo	0	1	/path/to/facts-tool
Clones (* active):
* 1		/path/to/facts-tool
```

**What this tells you:** `repo add` alone creates the project database and
registers a checkout clone. It does not create any components, directories,
or files yet (`COMPONENTS=0`), and it does not run git-root promotion here
because the given path already is the checkout root. See
[Repositories and Projects](../02-projects-and-configuration/01-repositories-and-projects.md)
for what each catalog level (repository, component, directory, file) means.

### 2. Import the compile database

```console
$ facts-tool import --conf project.sqlite --compilation-database build
facts-tool: incompatible-symbol-universe: unsupported facts schema version
$ echo $?
1
```

The command failed with exit code 1 and nothing was imported. On this
machine, a stale
`~/.cache/facts/<project>/facts.db` from earlier work (at a newer native
schema version than this build supports) is silently consulted for
call-graph-entry invalidation, even though `--facts` was never passed and
the failure has nothing to do with the compile database itself. This is
exactly the kind of surprise
[the configuration files chapter](../02-projects-and-configuration/03-configuration-files.md)
and
[`config show`](../02-projects-and-configuration/04-config-command.md)
exist to catch. The fix here is to always pass an explicit `--facts` on
`import` too, even though `import` itself does not write facts:

```console
$ facts-tool import --conf project.sqlite --facts facts.sqlite --compilation-database build
[1/360] Processing file .../src/storage/CallGraphEntry.cpp.
...
[360/360] Processing file .../src/commands/analyse/RecoveryScan.cpp.
Imported 360 compile command(s)
Registered 8869 file(s)
```

**What this tells you:** `import -p <dir>` imports **every** entry in
`compile_commands.json`, including third-party dependencies and tests
(360 compile commands total), and registers 8869 files, counting every
header pulled in transitively, not just the `.cpp` translation units. See
[Importing Compile Commands](../02-projects-and-configuration/02-importing-compile-commands.md)
for the full behaviour of `import -p`.

### 3. Scope extraction to the project's own sources

```console
$ find src -name '*.cpp' > src_files.txt   # 212 files
$ time facts-tool extract --conf project.sqlite -o facts.sqlite -v 0 $(cat src_files.txt)
... (many) facts-tool: coverage.unsupported_semantics kind=implicit-cleanup site=...
facts-tool: 15412 symbol(s) recorded from 769 file(s)
291.16s user 63.05s system 99% cpu 5:56.96 total
```

**What this tells you:** extracting 212 of the project's own `.cpp` files
still visits 769 files in total, because every header reachable from them
(including libc++ and Clang's own headers) is parsed too, and it takes
about six minutes wall-clock on this machine. `coverage.unsupported_semantics`
notices at `-v 0` are diagnostics about cleanup paths the extractor cannot
fully model (for example destructors inside libc++ templates), not
failures. See
[What Gets Extracted](../03-extracting-facts/02-what-gets-extracted.md)
and [Extract](../03-extracting-facts/01-extract.md).

### 4. Sanity-check with symbol and file listings

```console
$ facts-tool file list --conf project.sqlite | head -3
ID	COMPONENT	DIRECTORY	FILE	OVERRIDDEN	INDEXED	PATH
1	libtooling-lab	skeletons/facts-tool/build/_deps/ftxui-src/.../component	animation.cpp	false	false	...
... (8870 lines total)
$ facts-tool symbol list --facts facts.sqlite --conf project.sqlite | head -5
kind                qualified name
class               facts::callgraph::(anonymous namespace)::CallerSearch
constructor         facts::callgraph::(anonymous namespace)::CallerSearch::CallerSearch(...)
instance-method     facts::callgraph::(anonymous namespace)::CallerSearch::run(...)
```

Notice the `repository`/`component` columns here show `libtooling-lab`, not
`facts-tool`: it was `import -p` (not `repo add`) that actually created the
component, and it ran git-discovery, which promoted the component's
repository to the enclosing checkout. The `repo add facts-tool ...` row
from step 1 is a separate, orphan repository with 0 components. See
[Repositories and Projects](../02-projects-and-configuration/01-repositories-and-projects.md)
for why `repo add` and `import -p` can disagree about repository identity,
and
[Inspecting Symbols from the CLI](../03-extracting-facts/05-inspecting-symbols-cli.md)
for the full `symbol`/`file` command surface.

### 5. Touch one file and re-extract

```console
$ touch src/main.cpp
$ time facts-tool extract --conf project.sqlite -o facts.sqlite -v 1 src/main.cpp
facts-tool: extract: starting
... facts-tool: extract: Clang parse and AST extraction
facts-tool: 4 symbol(s) recorded from 2 file(s)
facts-tool: extract: complete
0.10s user 0.16s system 97% cpu 0.262 total
```

```console
$ time facts-tool extract --conf project.sqlite -o facts.sqlite -v 0 $(cat src_files.txt)
facts-tool: 15412 symbol(s) recorded from 769 file(s)   # identical counts to step 3
6:33 total   (slightly longer than the first run, not incremental)
```

**What this tells you:** `extract` is incremental only in the sense that
**you** choose the source list. Extracting one touched file is fast
(0.26s) and only regenerates that file's own symbols. There is no
automatic mtime- or hash-based skip at the whole-project level:
re-running `extract` over the same 212-file list re-parses and
re-persists everything from scratch every time, with the same symbol
count and the same roughly six minutes, regardless of whether any source
actually changed. "Incremental" extraction is a workflow you build
yourself, by extracting only the files you touched, not a built-in
freshness check.

### 6. Keep extra compiler flags consistent across commands

If the project needs non-default compiler flags (a specific `-std=`, a
project-only `-D` define), `import --extra-arg=X` only affects the compile
command stored by that one `import`. A separate small fixture makes this
concrete: a project pinning `-std=c++11` in `.facts-tool.yaml`, importing a
file that needs C++20 concepts with an explicit override:

```console
$ cat .facts-tool.yaml
extra_args: [-std=c++11]
$ facts-tool import --conf p2.db --facts f2.db --extra-arg=-std=c++20 cxx20_feature.cpp
Imported 1 compile command(s)
$ facts-tool extract --conf p2.db -o f2.db cxx20_feature.cpp        # no --extra-arg here
error: unknown type name 'T'   # concepts feature not usable, extraction fails
$ facts-tool extract --conf p2.db -o f2.db --extra-arg=-std=c++20 cxx20_feature.cpp
facts-tool: 4 symbol(s) recorded from 1 file(s)   # succeeds
```

**What this tells you:** `extract` (and `analyse dependency`) recompute
their own merged `extra_args` from YAML independently on every invocation,
unless you repeat the same `--extra-arg` there too, even though the project
database already stored a working command from `import`. The project's
`.facts-tool.yaml` silently won over what `import` had baked in. Either
repeat `--extra-arg` on every `import`/`extract`/`dependency`/`match`
invocation for a given source, or keep the flags only in YAML so every
command picks them up the same way. See
[Configuration Files](../02-projects-and-configuration/03-configuration-files.md)
for the full precedence model.

## Pitfalls

- **A stale `~/.cache/facts/<project>/facts.db` can break `import` even
  when you never reference it.** `facts_template` is still consulted for
  call-graph-entry invalidation unless you pass `--facts` explicitly, and
  the project identity used to resolve it comes from the nearest
  `.git`/`.facts-tool.yaml` above your current directory, not from
  `--conf`'s literal path. Always pass `--facts` on `import` too, and run
  `config show` first if a generated path looks unexpected.
- **`import -p DIR` pulls in the whole compilation database**, including
  third-party dependencies and tests, and registers every transitively
  included header as a file. Don't be surprised by large file counts; scope
  what you actually `extract` afterward with an explicit source list.
- **Whole-project `extract` is not incremental.** Re-running it over an
  unchanged file list re-parses and re-persists everything again, at the
  same cost. Scope your own re-extraction to touched files for speed.
- **`--extra-arg` given to `import` does not "stick" for later `extract`
  calls.** Repeat it on every compiler-consuming command for the same
  source, or rely solely on YAML `extra_args`.
